## Design Context

### Users
Sistema de controle de estoque usado em contexto misto entre operacao e administrativo. A prioridade principal e a operacao: leitura rapida, identificacao imediata de estados e densidade suficiente para tomada de decisao sob pressao, sem sacrificar o uso mais calmo de backoffice.

### Brand Personality
Tecnico, premium e preciso. A interface deve transmitir controle, confianca e clareza, nunca extravagancia, brilho gratuito ou cara de template generico.

### Aesthetic Direction
Dark mode only. Base escura com neutros frios, separacao clara entre fundo e superficies, e acento azul-acero controlado usado para orientar o olhar e comunicar estado. Sem focus rings visuais, sem glow, sem gradientes decorativos, sem visual "AI slop".

### Design Principles
1. Leitura operacional vem antes de efeito visual.
2. Hierarquia deve ser percebida em segundos por contraste, espaco e tipografia.
3. Tokens mandam no sistema; overrides locais sao excecao.
4. Estados de loading, vazio, erro e ativo precisam ser inequivocos.
5. O app deve parecer uma ferramenta precisa, nao um dashboard generico.

### Component Patterns

**StatCard** — padrao para metricas em todas as paginas.
`components/ui/stat-card.tsx`. Icone no canto superior direito, valor grande, label + subtitle. Nunca reinventar inline.

**SearchableSelect** — obrigatorio para campos com lista longa (clientes, pecas, fornecedores).
`components/ui/searchable-select.tsx`. Substitui `<Select>` quando a lista tem mais de ~8 itens ou precisa de busca.

**Modais** — estrutura fixa: header (icone + titulo + descricao) / `<ScrollArea>` / footer com botoes.
Fundo `bg-card`, header e footer separados por `border-b/t border-border`, padding `p-6`.

**AlertaGrid** — grid 2 colunas para itens de alerta com barra de progresso.
Usar quando ha 4+ itens homogeneos lado a lado — mais escaneavel que lista vertical.

**MovimentacaoTimeline** — timeline com trilho visual para historico/auditoria.
Usar quando o dado e puramente leitura e a ordem cronologica e relevante. Cards individuais so quando cada item tem acoes proprias.

---

### Interaction Patterns

**Validacao de formularios** — FieldErrors por campo com mensagem inline + toast com resumo no submit.
Re-validar em tempo real apos a primeira tentativa (flag `submitted`). Nunca bloquear sem comunicar qual campo falhou.

**Selecao de pecas em ordens** — SearchableSelect que adiciona a lista local com controles +/-.
Validar estoque no momento da selecao (toast imediato), nao so no submit.

**Colunas em mobile** — esconder colunas secundarias abaixo de `sm:` (640px).
Manter visíveis: identidade principal, status, acao. Esconder: contexto secundario, data.

---

### Anti-patterns

- Nao usar hex direto em componentes — sempre tokens (`bg-card`, `border-border`, etc.)
- Nao criar `<Select>` para listas longas — usar `SearchableSelect`
- Nao reinventar StatCard inline — importar o componente compartilhado
- Nao usar `rounded-[Xpx]` — usar `rounded-md`, `rounded-lg`, `rounded-xl`
- Nao usar `text-[Xpx]` exceto `text-[10px]` (sem equivalente nativo)
